Bug Workflow Redesign¶

Date: 2026-05-12
Status: Approved for implementation

Overview¶

Redesign the Forge bug workflow to add a triage stage, container-based code analysis, an RCA reflection loop, multi-option fix selection, and a planning/decomposition stage before implementation. The implementation stage and everything downstream (CI, human review) are unchanged.

Graph Structure¶

route_entry
    ↓
triage_check ─── sufficient ──→ analyze_bug ←──────────────────────┐
    │                                ↓                              │ (feedback)
    └── missing ──→ triage_gate      reflect_rca ──── gaps ──→ analyze_bug
                    (pause)     ↓         ↑                (max 3 iterations)
                          ──────┘    passes
                                     ↓
                              rca_option_gate (pause)
                                     ↓ >option N
                              plan_bug_fix (container)
                                     ↓
                              plan_approval_gate (pause, forge:plan-approved label)
                                     ↓
                              decompose_plan → linked Jira tasks
                                     ↓
                              [existing task execution loop]
                              setup_workspace → implement_bug_fix → local_review
                                  → create_pr → teardown_workspace
                                  → ci_evaluator → human_review_gate → END

New nodes: triage_check, triage_gate, reflect_rca, plan_bug_fix, regenerate_plan, plan_approval_gate, decompose_plan

Unchanged from current implementation: setup_workspace, implement_bug_fix, local_review, create_pr, teardown_workspace, ci_evaluator, attempt_ci_fix, human_review_gate, implement_review, review_response_gate, escalate_blocked, answer_question

Stage 1: Triage¶

triage_check (no container)¶

Calls the triage-bug prompt with the full Jira ticket content. Evaluates presence of six required fields:

  1. Steps to reproduce
  2. Expected vs actual behavior
  3. Environment (OS, runtime, infrastructure)
  4. Affected versions
  5. Error output (stack trace, log snippet, or error message)
  6. Affected component / repo

Sufficient path: all six present or clearly inferable → sets triage_passed: True, routes directly to analyze_bug.

Missing path: one or more absent → agent generates a targeted comment listing only the missing fields (not a generic form), posts to Jira, sets forge:triage-pending label, routes to triage_gate.

triage_gate (pause)¶

Pauses the workflow. On resume (reporter replies), triage_check runs again against the updated ticket (description + all comments). Repeats until all six fields are satisfied. No iteration limit.

Stage 2: Analysis¶

analyze_bug (standard container, repo access)¶

Receives: - Full Jira ticket (description + all comments including triage replies) - triage_missing_fields (fields that were thin even after triage, for awareness) - Previous reflection_critique if this is a re-run after critic feedback - User feedback if this is a re-run after rca_option_gate rejection

The agent explores the codebase: clones repos, checks out branches, reads files, inspects git history to locate the defect. It does not guess — it traces from trigger to symptom in the code.

Output RCA must include: - Confirmed location in code (file, function, line range) - Mechanism of failure (what the code does wrong) - Trace from trigger to symptom - 1–4 distinct fix options, each with title, description, and trade-offs - Embedded code snippets sufficient for the critic to validate without repo access

reflect_rca (standard container, repo access)¶

Receives the RCA text only (critic does not re-read the ticket). Validates: - Named files and functions exist at the stated locations - Failure mechanism is actually possible given the code - Fix options are genuinely distinct (not restatements of each other) - No unexplained gaps between trigger and symptom

Outputs either VALID or a structured critique listing specific gaps.

Loop behavior: if gaps exist, stores critique in reflection_critique and routes back to analyze_bug. Max 3 iterations. After the third failed reflection, the best available RCA is used and a note is appended to the Jira comment indicating the analysis was not fully validated.

Stage 3: RCA Option Gate¶

rca_option_gate (pause)¶

Posts a structured Jira comment on first entry:

## Root Cause Analysis

<rca summary>

## Fix Options

**Option 1: <title>**
<description and trade-offs>

**Option 2: <title>**
<description and trade-offs>

...

Reply with `>option N` to select an approach, or comment with feedback to revise the RCA.

Sets forge:rca-pending label (reuses existing label).

On resume, comment routing:

Comment Action
Starts with >option N (case-insensitive) Validate N is in range → store selected_fix_option and selected_fix_approach → route to plan_bug_fix
>option N out of range Post clarifying comment ("Option N doesn't exist, valid options are 1–M") → re-pause
No >option prefix Treat as RCA feedback → route to regenerate_rca → re-runs analyze_bug + reflect_rca loop → return to rca_option_gate
Question (Q&A mode) Route to answer_question → return to rca_option_gate

regenerate_rca¶

Passes original RCA, user feedback, and ticket context to analyze-bug (rewrite prompt: regenerate-rca.md). Reflection loop runs again on the result. Returns to rca_option_gate.

Stage 4: Planning¶

plan_bug_fix (standard container, repo access)¶

Receives full RCA and selected_fix_approach. Produces a concrete implementation plan scoped to the chosen approach: - Which files to change and what the changes accomplish - New tests required (regression coverage) - Order of operations - Which repos are involved

Posts the plan as a Jira comment and sets forge:plan-pending label.

## Implementation Plan

**Approach: <selected option title>**

### Changes
1. `path/to/file.py` — <what changes and why>
2. `path/to/test_file.py` — <new regression test>
...

### Repos
- `repo-name` (tag: repo:repo-name)

### Order of operations
<step-by-step sequence>

plan_approval_gate (pause)¶

Pauses workflow. Sets forge:plan-pending label.

On resume:

Trigger Action
forge:plan-approved label applied Route to decompose_plan
Plain comment Treat as feedback → route to regenerate_plan → re-runs plan_bug_fix → return to plan_approval_gate

regenerate_plan¶

Passes original plan and feedback to plan_bug_fix (via regenerate-plan.md prompt). Returns to plan_approval_gate.

decompose_plan (no container)¶

Reads the approved plan and creates one Jira Task per repo involved, linked to the bug ticket via "implements" issue link. Each task: - Gets a repo:<repo-name> label (same pattern as epic decomposition in feature workflow) - Contains scoped implementation instructions for its repo - Is stored in linked_task_keys

Single-repo fixes produce exactly one linked task. Every approved plan produces at least one linked task — if no repo is explicitly identified, the task is created against the primary repo from the ticket context.

State Changes¶

New fields added to BugState:

# Triage
triage_passed: bool
triage_missing_fields: list[str]

# Analysis / reflection
reflection_count: int
reflection_critique: str | None
rca_options: list[dict]          # [{title, description, tradeoffs}, ...]

# Option selection
selected_fix_option: int | None
selected_fix_approach: dict | None

# Planning
plan_content: str | None
linked_task_keys: list[str]      # Jira task keys created by decompose_plan

New ForgeLabel entries:

TRIAGE_PENDING = "forge:triage-pending"
PLAN_PENDING   = "forge:plan-pending"
PLAN_APPROVED  = "forge:plan-approved"

Prompts¶

All in src/forge/prompts/v1/:

File Status Purpose
triage-bug.md New Evaluate ticket against six-field checklist; output missing fields or "sufficient"
analyze-bug.md Rewrite Full container analysis with 1–4 fix options and embedded code evidence
regenerate-rca.md Rewrite Re-analyze incorporating user feedback on previous RCA; same output structure as analyze-bug.md
reflect-rca.md New Critic pass; output VALID or structured gaps
plan-bug-fix.md New Generate implementation plan from RCA + selected option
regenerate-plan.md New Revise plan incorporating user feedback
fix-bug.md Retired Replaced by implement-task prompt used with plan as context

Error Handling¶

All new nodes follow the existing pattern: exceptions are caught, stored in last_error, retry_count incremented. After max retries, escalate_blocked is called. Specific cases:

  • triage_check fails → retry up to 3x, then escalate
  • analyze_bug fails → retry up to 3x, then escalate
  • reflect_rca exceeds 3 iterations without VALID → use best RCA with warning note, continue
  • plan_bug_fix fails → retry up to 3x, then escalate
  • decompose_plan fails → escalate (no partial task creation)
  • Invalid >option N → post clarifying comment, re-pause (not an escalation)

What Is Not Changing¶

  • setup_workspace, implement_bug_fix, local_review, create_pr, teardown_workspace — unchanged
  • CI evaluation loop — unchanged
  • Human review / implement review loop — unchanged
  • Q&A mode wiring — extended to cover new gates (triage_gate, plan_approval_gate) using existing answer_question node
  • route_entry resume logic — extended to cover new nodes; all existing resume paths preserved
